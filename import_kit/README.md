# Step 5 — UnrealEd Import Kit

Goal: prove the **read → decode → generate-T3D** path produces something the engine
actually places correctly. We import a small, self-contained set of actors generated by
`ut2parser.py --t3d` into UnrealEd and confirm they land at the right coordinates.

There is **no `ucc` command to import T3D**, so this step is done in the UnrealEd GUI via
the clipboard (the `.t3d` text *is* UnrealEd's actor copy/paste format).

## Files in this kit
| File | Actors | Why it's a good test |
|------|-------:|----------------------|
| `DM-Rankin-PlayerStarts.t3d` | 16 | **Start here.** No mesh/texture dependencies, no enum bytes, no arrays. Each actor is just `Tag` + `Location` + `Rotation`. Renders as obvious player icons. Easy to count and spot-check. |
| `DM-Rankin-Lights.t3d` | 360 | Optional bigger test. Self-contained light actors; makes a clear constellation. |

Both were generated in `--t3d-clean` mode, which drops level-binding refs (`Level`,
`PhysicsVolume`, `Base`, nav links) so they paste into an empty level with **no
"object not found" warnings**.

## Import steps (PlayerStarts first)

1. **Launch UnrealEd.** `C:\UT2004\System\UnrealEd.exe` (or `UT2004.exe editor`).
   It opens on an empty `Untitled` level — that's fine; actors are visible without any
   geometry. (If not empty: **File → New** → blank.)
2. **Copy the T3D to the clipboard.** Open `DM-Rankin-PlayerStarts.t3d` in Notepad,
   **Ctrl+A**, **Ctrl+C**. (The `Begin Map … End Map` wrapper is exactly what UnrealEd's
   paste expects.)
3. **Paste into the level.** In UnrealEd: **Edit → Paste** (Ctrl+V). 16 PlayerStart actors
   appear at their original coordinates and stay selected.
4. **Frame them.** In a viewport, the camera/2D ortho views should show 16 red player-pawn
   icons. Use the top (X/Y) ortho viewport for the clearest layout; the spread should fill
   the bounds below.

## Verification checklist
- [ ] **Count = 16** PlayerStarts pasted (Edit → check selection, or the log line
      `Pasted N actors`).
- [ ] **No error dialogs / red log lines** during paste (clean mode should be silent).
- [ ] **Bounds look right** — the actors span roughly:
  - X: **−690 … 4724**
  - Y: **−2451 … 1202**
  - Z: **−465 … 47**
- [ ] **Spot-check one coordinate.** Select `PlayerStart8`, open its properties
      (F4 → Movement → Location). It should read **X=3456, Y=−384, Z=47**, Yaw=45056.
      (`PlayerStart1` should read **X=−32, Y=−640, Z=−273**, Yaw=7420.)

If those match, the round-trip is proven: our decoder read the binary, our generator wrote
T3D, and the engine placed the actors exactly where the original map had them.

## Optional: overlay test (stronger proof)
Instead of an empty level, **open `DM-Rankin` itself** in UnrealEd, then paste the
PlayerStarts. Each pasted PlayerStart should land **exactly on top of** an existing one
(z-fighting icons) — visual proof the coordinates are identical to the source.

## Then: the Lights
Repeat with `DM-Rankin-Lights.t3d` (360 actors) for a denser visual. Expect 360 light
actors; `LightBrightness`/`LightHue`/`LightSaturation` carry over (light *radius* uses
`LightRadius`, an array/extra prop we don't emit yet, so don't expect lighting to look
final — this is a placement test).

## Regenerate / customize
```sh
# from the repo root
python ut2parser.py Maps/DM-Rankin.ut2 --t3d --t3d-clean --t3d-class PlayerStart > import_kit/DM-Rankin-PlayerStarts.t3d
python ut2parser.py Maps/DM-Rankin.ut2 --t3d --t3d-clean --t3d-class Light      > import_kit/DM-Rankin-Lights.t3d
# any class / any map; omit --t3d-class for the whole map
```

## What this does NOT test yet
Brush/BSP geometry, bot-path networks (`PathList`), and enum-byte props are not emitted —
see the limitations in `../PROGRESS.md`. This kit validates **actor placement only**, which
is the first and most important link of the write pipeline.
